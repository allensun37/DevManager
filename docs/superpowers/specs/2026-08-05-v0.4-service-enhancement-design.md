# DevManager v0.4 Service Enhancement Design

状态：设计已批准，尚未开始编码。

## 1. 目标与范围

v0.4 将 v0.3 的本地 HTTP 工具提升为具有配置管理、日志、服务层和基础服务接口的小型 C++ 后端项目。

新增范围：

- Application Bootstrap；
- 本地 JSON 配置系统；
- Logger 适配层；
- ProjectService 服务层；
- HTTP 请求追踪；
- `GET /health`；
- `GET /api/info`；
- `GET /api/statistics`；
- OpenAPI 文档及 CI 格式校验。

明确不包含数据库、MySQL、Redis、Docker、Kubernetes、前端、用户系统、JWT、HTTPS、WebSocket、文件上传、微服务拆分和配置中心。

## 2. v0.3 基线

当前 v0.3 已具备：

- CLI 与本地 HTTP 两个入口；
- `ProjectManager`、`ProjectRepository`、`JsonProjectRepository` 分层；
- HTTP CRUD、搜索、筛选、排序和统一错误响应；
- JSON 快照校验、候选状态保存和失败回滚；
- ID 永不复用及溢出保护；
- GoogleTest 和 Ubuntu/Windows GitHub Actions；
- 91 个测试全部通过。

v0.4 不改变现有 CRUD、JSON 格式、ID 规则和 Repository 边界。

## 3. 总体架构

CLI 和 HTTP 都由各自的入口创建独立 Bootstrap。Bootstrap 只负责对象创建、依赖注入和生命周期，不包含业务规则。

```text
main / http_main
    |
    +-- ConfigLoader -> Config
    +-- LoggerFactory -> Logger
    |
    +-- JsonProjectRepository(Config.storage.path)
            |
        ProjectManager
            |
        ProjectService
            |
        ProjectHttpController
            |
        HttpServer(Config.server, Logger)
```

实现时建议由 `ApplicationComponents` 或等价的拥有者保存 Config、Logger、Repository、ProjectManager、ProjectService 和 HttpServer，确保依赖对象的生命周期覆盖使用者。

v0.4 仅让 HTTP 入口使用 ProjectService；CLI 保持现有 MenuController -> ProjectManager 路径，避免在本阶段扩大 CLI 重构范围。

## 4. Config 配置系统

文件：`config/devmanager.json`，路径相对于程序工作目录。

示例：

```json
{
  "server": {
    "host": "127.0.0.1",
    "port": 8080
  },
  "storage": {
    "path": "data/projects.json"
  },
  "logging": {
    "level": "info",
    "path": "logs/devmanager.log"
  }
}
```

规则：

- 配置文件不存在：使用默认配置；
- 配置文件存在但 JSON 损坏：启动失败；
- 配置字段类型错误或必填结构错误：启动失败；
- `storage.path` 和 `logging.path` 均相对于程序工作目录；
- 配置系统不读取环境变量，不连接配置中心，也不创建远程配置；
- Config 只保存和提供配置，不创建业务对象、不启动服务。

默认值：

```text
server.host = 127.0.0.1
server.port = 8080
storage.path = data/projects.json
logging.level = info
logging.path = logs/devmanager.log
```

## 5. 版本来源

版本唯一来源为 CMake：

```cmake
project(DevManager VERSION 0.4.0 LANGUAGES CXX)
```

CMake 通过编译定义或生成头文件提供 `DEVMANAGER_VERSION`，供 `/api/info` 使用。代码中禁止手写另一份版本字符串。README 和 Release 必须与该版本一致，并在发布阶段核对。

## 6. ProjectService

ProjectService 位于 Application 层，HTTP Controller 不再直接调用 ProjectManager。

职责：

- 聚合 CRUD、搜索、筛选和排序用例；
- 提供项目副本，不暴露 ProjectManager 内部容器引用；
- 计算 ProjectStatistics；
- 统一管理并发访问。

ProjectService 不依赖 `httplib`、`nlohmann::json`、HTTP 状态码或 spdlog。请求 DTO、响应 JSON 和错误码仍属于 HTTP/适配层。

## 7. 并发规则

唯一的项目状态锁归 ProjectService 所有。

- Controller 不持有 mutex；
- ProjectManager 不负责 HTTP 并发；
- Service 在一次业务操作和结果副本复制期间持锁；
- JSON 序列化、日志格式化和响应写入在释放项目锁后进行；
- Service 返回值类型为副本或独立 DTO；
- CLI 与 HTTP 仍不得同时写入同一个 `data/projects.json` 文件。

## 8. Logger

使用固定版本的 spdlog，通过 `infrastructure/logging/Logger` 适配，不跟踪 master。

Logger 边界：

- `Project`、`ProjectManager` 和 Domain 层不依赖 Logger 或 spdlog；
- LoggerFactory 由 Bootstrap 创建 Logger；
- HttpServer/Controller 记录 HTTP 请求、状态码、耗时和 request id；
- HTTP 边界记录 JSON 解析失败、Repository 失败和未预期异常；
- 客户端只获得稳定错误码和通用消息，不获得文件路径或内部异常细节。

日志规则：

- 服务启动记录 host、port 和版本；
- 日志目录不存在时自动创建；
- 默认文件为 `logs/devmanager.log`，也可由 `logging.path` 配置；
- 测试使用临时目录或 memory sink，不污染真实日志；
- v0.4 不要求异步日志、远程日志或日志中心。

## 9. HTTP 请求追踪

请求追踪在 HttpServer 层统一处理，覆盖正常响应、404、health、info 和异常响应。

规则：

- 请求头名称为 `X-Request-ID`；
- 客户端 ID 必须为 1～64 个字符；
- 允许字符为 ASCII 字母、数字、`.`、`_`、`-`；
- 缺失、过长或包含非法字符时由服务生成新的 ID；
- 服务始终在响应中返回 `X-Request-ID`；
- Logger 使用最终采用的 ID；
- 生成 ID 的实现不依赖 Domain，测试可以注入确定性的生成器或验证格式。

## 10. HTTP 新增接口

### `GET /health`

```json
{"status":"ok"}
```

语义为进程存活检查，不检查 JSON 文件内容或数据完整性。仓储初始加载失败时，入口启动失败，服务不会进入可访问状态。

### `GET /api/info`

```json
{
  "name": "DevManager",
  "version": "0.4.0"
}
```

版本来自 CMake 生成信息，不在 Controller 中手写。

### `GET /api/statistics`

```json
{
  "totalProjects": 10,
  "status": {"active": 5, "done": 5},
  "technology": {"c++": 8, "cmake": 6}
}
```

接口只读，不修改 Project 或持久化文件。

## 11. Statistics 规则

统计基于 ProjectService 获取的项目副本。

- status 使用 ASCII trim 后转 ASCII lowercase；
- technology 使用 ASCII trim 后转 ASCII lowercase，并保留标点，因此 `C++` 和 `c++` 统一为 `c++`；
- 同一个项目的重复技术标签只计一次；
- 统计结果按 key 稳定排序；
- 统计规则独立于搜索专用的技术栈匹配算法，避免把 `C++` 转成搜索用的 `cpp`；
- 空项目返回 `totalProjects: 0` 以及空的 status/technology 对象。

## 12. OpenAPI

新增 `docs/openapi.yaml`，覆盖：

- 现有项目 CRUD、查询参数和 JSON 字段；
- `/health`、`/api/info`、`/api/statistics`；
- 201、200、204、400、404、409、500 响应；
- `X-Request-ID` 请求头和响应头；
- 查询参数互斥规则及 sort 行为。

CI 使用固定版本的 YAML/OpenAPI 校验工具检查文件可解析性。OpenAPI 与实现不自动生成互相覆盖；每次接口契约变化必须同步修改实现、测试和文档。

## 13. 测试要求

继续采用“先失败测试，再实现，再运行完整测试”的流程。

新增覆盖：

- Config：默认值、正常读取、缺失文件、损坏 JSON、类型错误；
- Bootstrap：组件生命周期和依赖注入；
- Service：CRUD 代理、统计、返回副本、并发保护；
- Logger：初始化、临时目录、日志字段和错误消息脱敏；
- HTTP：health、info、statistics、request id、404、异常响应；
- OpenAPI：YAML 可解析及接口路径覆盖。

每个阶段都必须保留 v0.3 的 91 个回归测试。

## 14. 开发阶段

### Phase 1：Bootstrap、Config 和版本统一

完成 Application Components、ConfigLoader、默认配置、配置错误规则和 CMake 版本来源。

验收：配置/Bootstrap 测试通过，v0.3 的 91 个测试继续通过。

### Phase 2：ProjectService 迁移

完成 ProjectService 接口、唯一并发锁、返回副本和 Statistics 纯业务测试；Controller 改为调用 Service，现有 HTTP 行为不变。

验收：HTTP 现有测试和 Service 测试全部通过。

### Phase 3：Logger

完成 Logger 适配层、临时目录 sink、启动日志、HTTP 请求日志和错误日志脱敏。

验收：Logger 测试通过，Domain/Application 核心不依赖 spdlog。

### Phase 4：HTTP 增强

实现 `/health`、`/api/info`、`/api/statistics` 和 request id 生命周期。

验收：HTTP 集成测试覆盖正常、404、异常和请求追踪。

### Phase 5：OpenAPI

完成 `docs/openapi.yaml` 和 CI 固定工具校验。

验收：文档覆盖全部接口和错误契约。

### Phase 6：发布

完成 README、全量构建、Windows/Ubuntu CI 和 v0.4.0 Release。

验收：91 个 v0.3 回归测试及全部 v0.4 测试通过。

## 15. 开发边界

- 开始编码前再次检查当前 v0.3 代码和 91 个测试基线；
- 每阶段只修改本阶段范围；
- 保持 C++17、CMake、Windows/Linux CI；
- 不提前实现数据库、Redis、Docker、前端、认证或 HTTPS；
- 不把 Config、Logger、HTTP JSON 或 spdlog 引入 Domain 层。
