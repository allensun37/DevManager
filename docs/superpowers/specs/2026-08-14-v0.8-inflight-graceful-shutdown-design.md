# DevManager v0.8 In-Flight Graceful Shutdown Design

状态：设计已批准，尚未开始编码。

目标版本：v0.8.0

## 1. 目标

v0.8 只补强 v0.7 已有的优雅停止能力：用真实 HTTP 请求证明服务停止时，已开始处理的请求可以完成，服务不再接受新连接，监听线程和工作线程可以安全回收。

本版本不增加新的对外 HTTP API、配置项或业务能力。

| 模块 | 技术 |

## 3. 范围

新增：

- 一个仅供测试注入的 HTTP 请求控制钩子；
- 真实 in-flight HTTP 请求的停止、drain 和线程回收测试；
- drain deadline 超时后的安全收尾测试；
- 现有 Linux SIGTERM 检查和 Windows CTest 的回归验证。

不新增：

- 任何对外路由，例如 `/status` 或测试路由；
- Project、ProjectService、ProjectManager、Repository、存储、认证或分页语义；
- Docker、部署、服务管理器、配置系统或新的依赖库。

## 4. 架构边界

新增 `HttpServerTestHook`，它只属于 HTTP 测试边界。

```text
HTTP request
    |
API key authentication
    |
HttpServerTestHook (test injection only)
    |
ProjectHttpController
    |
ProjectService -> ProjectManager -> ProjectRepository
```

生产构造路径不提供该钩子，默认行为保持 v0.7 一致。测试构造路径以共享所有权注入钩子，使一个已认证的真实请求在进入 controller 前暂停和继续；`HttpServer` 持有该共享引用，确保钩子的生命周期覆盖可能访问它的 HTTP worker。

`HttpServerTestHook` 不依赖 ProjectService、ProjectManager、Repository、JSON、SQLite 或 Logger；它不引入可被外部调用的 HTTP 端点。钩子只负责确定性同步：报告请求已进入、等待测试释放。钩子内不写 GoogleTest 断言，不吞掉或跨 HTTP worker 传播测试异常；测试线程通过 `waitUntilEntered()` 等控制方法完成断言。

## 5. 停止语义

正常路径：

```text
已认证请求进入并暂停
    |
收到停止请求
    |
Readiness: Ready -> Stopping
HttpServer stopAccepting()
    |
确认监听 socket 已关闭、不再接受新连接
    |
fresh connection fails
    |
释放暂停请求
    |
请求正常返回
listener / worker 安全结束并 join
    |
Readiness: Stopped
ServiceExit: Stopped
```

停止开始后，不得接受新的 HTTP 连接。`Stopping` 本身不是 socket 已关闭的证明；`stopAccepting()` 调用 `server.stop()` 返回后，必须发布一个“停止接受已生效”的确认信号，测试只在收到该确认后使用新建 HTTP client 建立 fresh connection。不得把“listener 线程已结束”当作这个确认条件，因为 listener 的结束可能需要等待 in-flight 请求完成。

暂停中的请求不得被强制取消；它在测试显式释放后正常完成。

`drained` 的定义为：监听已停止、所有已经进入 HTTP handler 的请求均已退出、`HttpServer` 所拥有的 listener 线程已经可以安全 join；完成 drain 后，不存在仍访问 `HttpServer` 生命周期资源的 handler 或 worker。

`ShutdownTimeout` 仍是 v0.7 已定义的 drain-result deadline：在 deadline 内没有 drain 完成时，生命周期返回 `ShutdownTimeout` 并记录日志；它不 detach 线程、不强杀线程，也不以不安全方式销毁 `HttpServer`。

`ServiceExit` 与运行时最终状态是不同概念。超时后，`ServiceExit::ShutdownTimeout` 必须保持为本次停止操作的结果；Readiness 保持 `Stopping`。测试随后释放请求并执行安全 drain/join，生命周期再通过最小的“drain 后完成停止”步骤将 Readiness 标记为 `Stopped`，但不得把既有的 `ShutdownTimeout` 改写为 `Stopped`。

## 6. 测试设计

### 6.1 正常 drain 集成测试

1. 启动真实 `HttpServer`，确认 `/health` 与 `/ready` 可用；
2. 发送一个带正确 API key 的现有只读业务请求：`GET /api/projects`；
3. 测试钩子确认请求已经进入暂停点；
4. 请求停止；
5. 等待“停止接受已生效”确认；使用新建 HTTP client 建立 fresh connection，并断言该连接无法建立或无法完成 HTTP 请求；
6. 释放暂停请求；
7. 断言原请求正常返回，`waitUntilDrained()` 在 deadline 内完成，生命周期结果为 `Stopped`；
8. 断言服务器可安全析构，所有拥有的线程可 join。

### 6.2 超时后安全收尾测试

1. 以受控请求保持 in-flight 状态；
2. 使用很短的 drain deadline 请求停止；
3. 断言结果为 `ShutdownTimeout`，而不是伪装为已 drain；
4. 释放暂停请求；
5. 断言最终可安全等待 drain 并回收线程，Readiness 变为 `Stopped`，但 `ServiceExit` 仍为 `ShutdownTimeout`。

### 6.3 回归范围

- v0.7 的 `/health`、`/ready`、1 MiB payload 限制、API key 认证与错误 JSON；
- 项目 CRUD、查询、分页、JSON/SQLite 后端；
- Linux 的进程级 SIGTERM 脚本；
- Windows 与 Ubuntu 的 CTest。

## 8. 风险与约束

- 不用 sleep 作为状态正确性的依据；暂停和释放必须由 C++17 兼容的 `std::mutex`、`std::condition_variable` 或等价的确定性同步完成。
- 测试异常路径必须释放暂停请求，避免 CTest 挂起。
- 不将测试钩子暴露成生产配置、环境变量或 HTTP endpoint。
- 不承诺永久卡死的 worker 会在 deadline 内被强制终止；v0.8 保持 v0.7 的安全 join 契约。

## 9. 验收标准

- 真实 in-flight 请求完成后可优雅停止；
- 停止后不再接受新连接；
- 超时结果准确且可安全收尾；
- 运行时可完成 drain、join 与安全析构；代码约束中禁止 `detach` 与强杀 worker；
- 不破坏现有公开 API、认证、分页、持久化与 v0.7 生命周期语义；
- Windows 与 Ubuntu CI 均通过完整 CTest。
