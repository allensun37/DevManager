# DevManager v0.5 Database Persistence Design

状态：设计已于 2026-08-08 批准，尚未开始编码。
目标版本：v0.5.0

## 1. 目标

DevManager v0.5 在 v0.4 的 CLI、HTTP、配置、日志、请求追踪、OpenAPI 和测试体系上增加可替换的 SQLite 持久化后端，并让筛选与分页能够由存储层执行。

本版本的核心目标是：

- 保留 JSON 后端和现有用户数据的默认可见性；
- 增加可选的 SQLite 后端；
- 维持项目 ID 永不复用和保存失败回滚语义；
- 引入可扩展的数据库 Migration；
- 为项目查询增加确定性排序与分页；
- 不无意破坏 v0.4 已发布的 HTTP 成功响应契约。

## 2. 范围

v0.5 包含：

- JSON / SQLite 可配置存储后端；
- `RepositoryFactory`；
- Repository 实体级 CRUD、查询与计数契约；
- `ProjectQuery` 和 `PagedProjects`；
- SQLite 连接、事务、外键、索引；
- `schema_migrations` 和首个 Migration；
- HTTP 可选分页；
- 现有名称、状态、技术栈过滤在 SQLite 中执行；
- OpenAPI、GoogleTest、Ubuntu / Windows CI 更新。

v0.5 不包含：

- MySQL、PostgreSQL、Redis 或 ORM；
- Docker、Kubernetes、前端或云部署；
- 用户、认证、授权或 JWT；
- 数据库连接池；
- JSON 与 SQLite 双写；
- 自动 JSON 到 SQLite 数据迁移；
- Statistics 的 SQL 聚合优化；
- HTTP API 版本化或其他 v0.6 功能。

## 3. 兼容性决策

### 3.1 默认存储仍为 JSON

缺少配置文件时继续使用：

```text
storage.type = json
storage.path = data/projects.json
```

SQLite 必须显式配置：

```json
{
  "storage": {
    "type": "sqlite",
    "path": "data/devmanager.db"
  }
}
```

路径默认值随选中的后端确定：

- `storage.type` 缺失或为 `json`，且 `storage.path` 缺失：`data/projects.json`；
- `storage.type` 为 `sqlite`，且 `storage.path` 缺失：`data/devmanager.db`；
- 显式 `storage.path` 始终覆盖对应后端的默认路径。

这样可以保证升级到 v0.5 后，现有 `data/projects.json` 不会因默认切换而看似丢失。未知 `storage.type` 导致启动失败，并返回明确配置错误。

### 3.2 不自动搬迁数据

JSON 与 SQLite 是互斥的活动后端。切换后端不会复制、合并或删除另一后端的数据。一次性 Storage Migration Tool 不属于 v0.5。

### 3.3 保留 v0.4 列表响应

`GET /api/projects` 未显式提供 `page` 或 `size` 时，继续返回全部匹配项目的 JSON 数组。

显式提供 `page` 或 `size` 时仍返回 JSON 数组，分页元数据放入响应头：

```text
X-Total-Count
X-Page
X-Page-Size
```

因此 v0.5 不把成功响应改成 `{items, page, size, total}`，避免破坏 v0.4 客户端。

## 4. 总体架构

```text
CLI / HTTP
    |
ProjectService
    |
ProjectManager
    |
ProjectRepository
    +--------------------------+
    |                          |
JsonProjectRepository   SqliteProjectRepository
                               |
                        SqliteConnection
                               |
                        MigrationManager
```

启动对象图：

```text
ApplicationBootstrap
    |
    +-- Config
    +-- RepositoryFactory
            +-- JsonProjectRepository
            +-- MigrationManager -> SqliteProjectRepository
    +-- ProjectManager
    +-- ProjectService
    +-- CLI / HTTP adapters
```

统一使用当前代码中的接口名 `ProjectRepository`，不重新引入 `IProjectRepository`。

`ApplicationBootstrap` 持有 `std::unique_ptr<ProjectRepository>`。Repository 的生命周期必须覆盖引用它的 `ProjectManager`，Manager 的生命周期必须覆盖 `ProjectService`。

## 5. 职责边界

### 5.1 Project

`Project` 保持现有业务含义，仅包含：

- id；
- name；
- techStack；
- description；
- status。

它不依赖 SQL、SQLite、HTTP、Migration、分页或 RepositoryFactory。

### 5.2 ProjectManager

`ProjectManager` 继续负责：

- CRUD 业务规则；
- 字段校验；
- ID 分配和溢出保护；
- 候选状态构造；
- Repository 查询转发；
- Repository 保存成功后再替换内存状态。

它不解析 HTTP 参数，不执行 SQL，不管理 SQLite 连接。

### 5.3 ProjectService

`ProjectService` 继续作为 HTTP 使用的应用服务层，负责：

- 并发锁；
- CRUD 编排；
- `page` / `size` 校验和 offset 计算；
- 查询调用和 `PagedProjects` 组合；
- 现有 Statistics 逻辑。

Controller 不直接访问 Repository。

### 5.4 RepositoryFactory

`RepositoryFactory` 位于 infrastructure / repository 层，仅根据 Config 创建后端：

- `json`：创建 `JsonProjectRepository`；
- `sqlite`：打开连接、执行 Migration，再创建 `SqliteProjectRepository`。

Factory 不包含项目业务规则。JSON 启动不打开 SQLite，也不执行 Migration。

## 6. Repository 契约

### 6.1 启动边界

保留：

```cpp
ProjectStore loadStore();
```

它用于启动时恢复 `projects` 和持久化的 `nextId`。SQLite 允许在启动时加载当前项目到 Manager 内存，以维持 v0.4 CRUD、CLI 和 Statistics 行为。

`saveStore()` 不再是 SQLite 正常写入的主要抽象。迁移期间可临时保留兼容实现，但 Phase 4 完成后，正常 CRUD 必须使用实体级方法。

### 6.2 目标能力

```cpp
virtual void create(const Project& project, ProjectId nextIdAfterCreate) = 0;
virtual void update(const Project& project) = 0;
virtual void remove(ProjectId id) = 0;
[[nodiscard]] virtual std::optional<Project> findById(ProjectId id) const = 0;
[[nodiscard]] virtual std::vector<Project> query(const ProjectQuery& query) const = 0;
[[nodiscard]] virtual std::uint64_t count(const ProjectQuery& query) const = 0;
```

接口继续沿用当前异常边界：合法业务请求中的“项目不存在”由 `bool` / `std::optional` 表达；输入违反领域规则使用 `std::invalid_argument`；配置、文件、SQLite 和 Migration 失败使用 `std::runtime_error` 或更具体的标准库派生异常，并由 HTTP 层映射为现有安全错误响应。v0.5 不新建一套领域异常层级。

目标方法必须满足以下语义：

- `create` 原子保存项目、标签和 `nextIdAfterCreate`；
- `update` 原子保存项目字段和完整标签集合；
- `remove` 删除项目和标签，但不修改 `nextId`；
- `findById` 不存在时返回空结果，不伪造项目；
- `query` 在存储层完成过滤、排序和分页；
- `count` 使用与 `query` 相同的过滤条件，但忽略排序、offset 和 limit。

### 6.3 候选状态与回滚

每次写操作遵循：

```text
当前 ProjectStore
    -> 构造候选 ProjectStore
    -> 调用 Repository 实体写操作
    -> Repository 成功
    -> 替换 Manager 内存状态
```

Repository 失败时：

- 项目列表保持不变；
- `nextId` 保持不变；
- JSON 原文件保持不变；
- SQLite Transaction 回滚；
- HTTP / CLI 接收到现有统一失败语义。

JSON Repository 的实体级方法内部继续复用“候选完整快照 + 同目录临时文件 + 安全替换”策略。SQLite Repository 使用事务，不通过全表删除后重建模拟 CRUD。

Repository 成功后的内存提交必须使用预先构造好的候选对象和不会抛出异常的交换操作，避免出现“数据库已提交但 Manager 因二次分配失败而未更新”的状态。

## 7. ID 与 nextId

### 7.1 业务类型不变

`ProjectId` 保持 `std::uint64_t`。现有规则保持：

- 全新或缺失的仓库以 `nextId == 1` 初始化；
- 删除全部项目后的仓库允许 `nextId > 1`，用于保留历史高水位；
- ID 大于 0 且唯一；
- 非空仓库 `nextId` 大于所有已有 ID；
- 删除后 ID 不复用；
- `nextId` 不回退；
- `nextId == UINT64_MAX` 时拒绝新增，内存和持久化均不变化。

因此最大可新分配 ID 是 `UINT64_MAX - 1`。

### 7.2 SQLite 表示

SQLite `INTEGER` 是有符号 64 位，不能完整表示当前 `std::uint64_t` 契约。v0.5 使用固定 20 位、左侧补零的十进制 `TEXT` 保存项目 ID、外键和 `nextId`，例如：

```text
00000000000000000001
18446744073709551615
```

规则：

- 必须恰好 20 个 ASCII 数字；
- 解析必须严格检查 `uint64_t` 范围；
- 项目 ID 不允许为 0；
- 固定宽度保证 SQLite 文本升序与无符号数值升序一致；
- 外键列使用同一表示。

不得把 ID 强制转换为 `sqlite3_int64`，也不得悄悄把边界缩小为 `INT64_MAX`。

## 8. SQLite Schema

首版逻辑结构：

```sql
CREATE TABLE repository_state
(
    singleton INTEGER PRIMARY KEY CHECK(singleton = 1),
    next_id TEXT NOT NULL CHECK(
        length(next_id) = 20 AND
        next_id NOT GLOB '*[^0-9]*' AND
        next_id >= '00000000000000000001' AND
        next_id <= '18446744073709551615'
    )
);

CREATE TABLE projects
(
    id TEXT PRIMARY KEY CHECK(
        length(id) = 20 AND
        id NOT GLOB '*[^0-9]*' AND
        id >= '00000000000000000001' AND
        id <= '18446744073709551614'
    ),
    name TEXT NOT NULL,
    normalized_name TEXT NOT NULL,
    description TEXT NOT NULL,
    status TEXT NOT NULL,
    normalized_status TEXT NOT NULL,
    status_sort_key TEXT NOT NULL
);

CREATE TABLE project_tags
(
    project_id TEXT NOT NULL,
    position INTEGER NOT NULL CHECK(position >= 0),
    tag TEXT NOT NULL,
    normalized_tag TEXT NOT NULL,
    PRIMARY KEY(project_id, position),
    FOREIGN KEY(project_id)
        REFERENCES projects(id)
        ON DELETE CASCADE
);
```

索引至少包括：

```sql
CREATE INDEX idx_projects_normalized_status
ON projects(normalized_status);

CREATE INDEX idx_project_tags_normalized_tag
ON project_tags(normalized_tag);

CREATE INDEX idx_project_tags_project_id
ON project_tags(project_id);
```

设计说明：

- 不加入 `created_at` / `updated_at`，因为 v0.5 的 `Project` 没有这些字段，接口也不使用它们；
- `position` 保留技术栈原始顺序；
- 同一项目的原始重复标签继续可往返保存，避免 SQLite 后端悄悄改变现有模型；
- `normalized_tag` 仅用于搜索，不设置唯一约束；
- 名称使用前导通配符子串搜索，普通 B-tree 不能保证优化该查询，因此本版本不宣称名称索引带来性能收益。

`repository_state` 首次创建时初始化为一行，`next_id` 为 `00000000000000000001`。删除全部项目时不得重置该值。

两个后端的 `loadStore()` 都必须执行完整快照语义校验：项目 ID 大于 0 且唯一；`nextId` 大于 0；非空仓库 `nextId` 大于所有项目 ID。当前项目为空时不能据此判断仓库从未使用，因此允许已经前进的 `nextId`。SQLite 表约束不是该应用层校验的替代品。

## 9. 文本标准化与查询语义

当前搜索标准化逻辑从 `ProjectManager` 的局部实现移到 common 层纯工具组件，JSON、SQLite 和业务层复用同一规则。

规则保持 v0.4 行为：

- name：ASCII 大小写不敏感的子串匹配；
- status：ASCII trim + lowercase 后精确匹配；
- technology：复用现有技术栈标准化和子串匹配规则，例如 `C++` 与 `cpp` 语义一致；
- name 排序：ASCII lowercase 原始名称，不额外 trim；
- status 排序：ASCII lowercase 原始状态，不额外 trim；
- 非 ASCII 文本不做 Unicode 大小写折叠或本地化排序。

SQLite 在写入和更新时同步维护规范化列；`normalized_status` 用于筛选，`status_sort_key` 用于保持 v0.4 排序行为。查询时使用相同工具规范化条件。两个 Repository 不得各自复制一套不同规则。

## 10. ProjectQuery 与排序

查询模型位于 application / query 边界，不依赖 HTTP：

```cpp
struct ProjectQuery
{
    std::optional<std::string> name;
    std::optional<std::string> status;
    std::optional<std::string> technology;
    ProjectSortKey sort = ProjectSortKey::Id;
    std::uint64_t offset = 0;
    std::uint64_t limit = 0;
};
```

`limit == 0` 表示不分页，用于保持 v0.4 的完整列表语义。

排序规则：

- 默认按 ID 升序；
- name 按 ASCII lowercase 原始名称升序，相同名称按 ID 升序；
- status 按 ASCII lowercase 原始状态升序，相同状态按 ID 升序；
- 所有分页查询必须带确定性排序；
- JSON 和 SQLite 必须返回相同顺序。

HTTP 层继续保持 v0.4 限制：`name`、`status`、`technology` 最多出现一个，`sort` 可与其中一个组合。v0.5 不扩展为多过滤条件组合。

## 11. 分页模型与校验

内部返回模型：

```cpp
struct PagedProjects
{
    std::vector<Project> items;
    std::uint64_t total;
    std::uint64_t page;
    std::uint64_t size;
};
```

`PagedProjects` 只用于显式分页请求。未分页请求调用返回 `std::vector<Project>` 的查询用例，不使用 `page = 0`、`size = 0` 等哨兵值。

HTTP 规则：

- `page` 和 `size` 都不存在：不分页；
- 只有 `page`：`size = 20`；
- 只有 `size`：`page = 1`；
- `page >= 1`；
- `1 <= size <= 100`；
- 参数必须是严格十进制正整数，不接受符号、小数、空串或尾随字符；
- `(page - 1) * size` 必须先做溢出检查；
- 非法分页返回 `400 invalid_query`，保持现有错误分类；
- 超出末页返回空数组和正确的分页响应头，不返回 404。

Repository 的 `count` 返回匹配总数。若存储总数无法表示应用层计数类型，明确失败，不截断。

## 12. SQLite Connection 与事务

### 12.1 固定依赖

v0.5 固定使用 SQLite 3.53.4 官方 amalgamation：

```text
https://www.sqlite.org/2026/sqlite-amalgamation-3530400.zip
SHA3-256 628a44cfe82c66aed1ccbbe85a562d2e33ebe64b3288981ed76285612227934e
```

CMake 通过 `FetchContent` 下载并校验该归档，直接将 `sqlite3.c` 编译为项目内部静态 C target。顶层 `project()` 因此从只启用 `CXX` 调整为 `LANGUAGES C CXX`。不依赖操作系统预装 SQLite，也不下载预编译 DLL。

### 12.2 连接生命周期

`SqliteProjectRepository` 通过 RAII 对象持有单个 `sqlite3*` 连接：

```text
open
  -> configure
  -> PRAGMA foreign_keys = ON
  -> verify PRAGMA foreign_keys == 1
  -> ready
```

析构时检查并关闭连接。v0.5 不实现每条 SQL 单独开关连接，也不实现连接池。

所有 statement 必须使用参数绑定和 RAII 释放，不拼接用户输入。所有 SQLite 返回码均需检查并转换为不泄漏 SQL 或文件内部细节的应用错误。

事务边界：

- create：项目、全部 tags、`nextIdAfterCreate`；
- update：项目字段、删除旧 tags、写入新 tags；
- remove：项目删除和外键级联；
- 每个 migration：schema 变更和 migration 记录。

任一步骤失败必须回滚。

当前 HTTP 并发仍由 `ProjectService` 的唯一锁串行保护。Repository 不新增第二套业务互斥策略；SQLite 封装仍保证资源释放和失败安全。

## 13. Migration

Migration 源文件保存在：

```text
database/migrations/001_init.sql
```

为避免运行时依赖当前工作目录，构建阶段把已批准的 migration 内容嵌入可执行文件。数据库路径仍按 Config 相对程序工作目录解析。

状态表：

```sql
CREATE TABLE schema_migrations
(
    version INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    applied_at TEXT NOT NULL
);
```

执行规则：

- 内置 migration 在启动前按版本升序校验；
- 重复版本号导致初始化失败；
- 已执行版本不重复执行；
- 数据库含有程序未知的更高版本时启动失败，避免旧程序操作新 schema；
- 每个 migration 在独立事务中执行；
- SQL 和 `schema_migrations` 记录必须同一事务提交；
- 失败时启动失败且该 migration 不留下部分 schema；
- JSON 后端不执行 Migration。

## 14. 写入与查询数据流

### 14.1 新增项目

```text
Controller / CLI
  -> ProjectService（HTTP 路径持锁）
  -> ProjectManager 校验并构造候选 ProjectStore
  -> Repository.create(project, candidate.nextId)
       -> JSON 原子替换 或 SQLite Transaction
  -> Repository 成功
  -> ProjectManager 提交候选内存状态
```

### 14.2 查询项目

```text
HTTP query parameters
  -> Controller 严格解析
  -> ProjectService 校验分页并构造 ProjectQuery
  -> ProjectManager 转发 query / count
  -> Active Repository 执行过滤、排序、分页
  -> Controller 输出 JSON 数组和可选分页 Header
```

SQLite 查询不得 `SELECT all` 后交给 Application 做过滤和分页。JSON Repository 可以在内存中执行相同 `ProjectQuery`，但必须复用统一标准化和排序规则。

### 14.3 Statistics

v0.5 保持现有 Statistics 语义和 Manager 内存快照，不新增 `GROUP BY` 查询。SQLite 启动时加载 ProjectStore，写成功后更新同一内存状态，因此 Statistics 与 CRUD 一致。

## 15. 错误处理

必须区分并测试：

- 配置错误：未知 storage type、字段类型错误；
- 数据库打开或初始化失败；
- migration 版本或 SQL 失败；
- SQLite CRUD / query / count 失败；
- 持久化数据语义无效；
- 分页或查询参数非法；
- 项目不存在；
- `nextId` 溢出。

HTTP 客户端只获得稳定错误码和安全消息。SQL、绝对路径、原始 SQLite 错误文本写入服务端日志，不直接进入响应正文。

## 19. 开发规则

1. 实现前以 v0.4 实际代码为准，不根据旧文档猜接口。
2. 每阶段先写失败测试，再实现，并运行完整回归。
3. 统一使用 `ProjectRepository` 命名。
4. 不把 SQLite、SQL、HTTP 或分页细节放入 `Project`。
5. Controller 不访问 Repository，ProjectManager 不执行 SQL。
6. 保留候选状态提交和持久化失败回滚。
7. 保留 `std::uint64_t` ID、`nextId` 和 ID 永不复用规则。
8. JSON 与 SQLite 的项目、搜索、排序和分页语义一致。
9. SQLite 写操作和 Migration 使用事务，并启用外键。
10. 不双写，不自动迁移用户 JSON 数据。
11. 默认后端保持 JSON。
12. 不破坏 v0.4 无分页列表成功响应。
13. 保持 C++17、CMake、GoogleTest 和 Ubuntu / Windows CI。
14. 不提前加入数据库以外的 v0.6 技术。

## 20. 最终验收

v0.5 完成时必须能够证明：

- 相同业务测试可在 JSON 和 SQLite 后端通过；
- SQLite 查询、过滤、排序和分页真正由 SQL 执行；
- Migration 可重复、失败可回滚；
- 外键和写事务通过测试验证；
- `nextId` 跨重启持久化且永不回退；
- `uint64_t` ID 不因 SQLite 有符号整数而缩小范围；
- v0.4 HTTP 客户端在未使用分页参数时继续正常工作；
- 全量测试与双平台 CI 通过。
