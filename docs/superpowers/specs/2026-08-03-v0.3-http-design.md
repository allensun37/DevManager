# DevManager v0.3 HTTP 服务设计

状态：设计已批准，尚未开始编码。

## 目标

在 v0.2 命令行版本的基础上增加一个本地 HTTP 接口，使现有项目管理能力可以通过 REST/JSON 调用。v0.3 不改变现有业务规则，不引入数据库、Redis、Docker、前端、认证、日志系统或配置系统。

## 范围

HTTP 只暴露 v0.2 已有能力：

- 新增、编辑和删除项目；
- 列出项目；
- 按名称或技术栈搜索；
- 按状态筛选；
- 按 ID、名称或状态升序排序。

以下内容明确不在范围内：

- 单项目查询接口；
- PATCH 局部编辑；
- 多条件组合筛选；
- 分页、认证、授权、API 版本化和异步任务；
- 数据库、Redis、Docker、Web 页面、日志和配置中心。

## 分层架构

```text
devmanager_http
    └── HttpServer
          └── ProjectHttpController
                └── ProjectManager
                      └── ProjectRepository
                            └── JsonProjectRepository
```

### HttpServer

`HttpServer` 是 HTTP 传输适配器，负责：

- 持有并配置 `cpp-httplib::Server`；
- 注册项目路由；
- 监听和停止服务；
- 暴露测试所需的动态端口和停止能力。

它不实现项目业务规则，也不直接操作仓储。

### ProjectHttpController

`ProjectHttpController` 负责：

- 读取路径、查询参数和请求 JSON；
- 严格解析项目 ID；
- 将请求字段转换为 `ProjectManager` 参数；
- 将 `Project` 转换为 HTTP JSON；
- 将业务异常和返回值映射为 HTTP 状态码和错误码。

HTTP 类型、JSON 请求和响应只停留在 HTTP 层，不进入 `ProjectManager`、`Project` 或 `ProjectRepository`。

### 现有层

`ProjectManager`、`ProjectRepository`、`JsonProjectRepository` 和 `MenuController` 保持职责不变。CLI 和 HTTP 两个入口共享 domain、application 和 repository 库，但彼此不依赖。

## HTTP 可执行目标

保留现有 `DevManager` 循环菜单程序，新增独立的 `devmanager_http` 可执行文件：

- `DevManager`：现有 CLI；
- `devmanager_http`：HTTP 服务入口。

HTTP 入口默认构造 `JsonProjectRepository("data/projects.json")` 和 `ProjectManager`，然后启动 `HttpServer`。加载失败时沿用现有启动失败行为，由入口捕获异常并以非零状态退出。

## 路由契约

### 列表、搜索、筛选和排序

```text
GET /api/projects
```

支持的查询参数：

- `name`：按名称搜索；
- `technology`：按技术栈搜索；
- `status`：按状态筛选；
- `sort=id|name|status`：升序排序。

`name`、`technology`、`status` 最多出现一个；`sort` 可以和其中一个条件同时出现。多个搜索/筛选参数同时出现时返回 `400 invalid_query`。不提供查询参数时返回完整项目列表。

查询参数的空白和大小写处理继续由现有 `AsciiText` 与 `ProjectManager` 规则负责，HTTP 层不复制业务匹配逻辑。

### 新增项目

```text
POST /api/projects
```

请求体：

```json
{
  "name": "DevManager",
  "techStack": ["C++", "CMake"],
  "description": "项目管理工具",
  "status": "active"
}
```

客户端不得提供 `id`。ID 由 `ProjectManager` 生成，并继续遵守不复用和溢出规则。

成功返回 `201 Created` 和完整项目对象。

### 编辑项目

```text
PUT /api/projects/{id}
```

请求体必须包含 `name`、`techStack`、`description` 和 `status`。路径中的 ID 是唯一 ID 来源，项目原 ID 保持不变；请求体中的 `id` 不接受或按非法字段处理。

成功返回 `200 OK` 和更新后的完整项目对象。项目不存在返回 `404 project_not_found`。

### 删除项目

```text
DELETE /api/projects/{id}
```

成功返回 `204 No Content`。项目不存在返回 `404 project_not_found`。删除确认只属于 CLI 交互，HTTP 不模拟 y/Y 确认。

## JSON 格式

项目对象沿用现有字段名和类型：

```json
{
  "id": 1,
  "name": "DevManager",
  "techStack": ["C++", "CMake"],
  "description": "项目管理工具",
  "status": "active"
}
```

- `id` 为正整数；
- `techStack` 为非空字符串数组；
- `name` 和 `status` 不得为空白；
- `description` 可以为空。

成功响应不使用额外 `data` 包装：列表直接返回数组，新增和编辑直接返回项目对象，删除返回空响应。

## 错误契约

所有错误返回 JSON：

```json
{
  "error": {
    "code": "project_not_found",
    "message": "项目不存在"
  }
}
```

状态码和错误码：

| 状态码 | 错误码 | 场景 |
|---|---|---|
| 400 | `invalid_json` | 请求体不是合法 JSON |
| 400 | `invalid_request` | 字段缺失、类型错误或项目校验失败 |
| 400 | `invalid_id` | ID 不是正整数或发生溢出 |
| 400 | `invalid_query` | 查询参数组合或排序键非法 |
| 404 | `project_not_found` | 目标项目不存在 |
| 500 | `persistence_failure` | 保存、替换或其他仓储操作失败 |
| 500 | `internal_error` | 未预期的内部错误 |

不向客户端暴露底层堆栈和文件系统细节；服务端保留现有异常处理行为，不新增日志系统。

## 运行约束

- 默认监听 `127.0.0.1:8080`，只允许本机访问；
- HTTP 与 CLI 复用 `data/projects.json`；
- 暂不保证 CLI 和 HTTP 同时运行时的并发写入安全，文档中明确要求避免同时写入；
- 服务主线程阻塞运行；
- `HttpServer` 提供 `stop()` 供测试关闭服务，不增加后台守护或复杂信号管理。

## 依赖和构建

- 保持 C++17；
- 使用 `cpp-httplib` 提供 HTTP 服务和测试客户端；
- 依赖通过 CMake 管理，并固定可复现的版本或提交；
- 新增 HTTP 库目标、HTTP 可执行目标和 HTTP 测试目标；
- 原 CLI、现有测试和双平台 CI 行为保持不变。

## 测试设计

HTTP 测试使用进程内回环集成方式：

- 测试线程启动 `HttpServer`；
- 绑定 `127.0.0.1` 动态端口；
- 使用 `httplib::Client` 发送真实 HTTP 请求；
- 测试结束调用 `stop()`；
- 每个测试使用独立临时数据目录或失败注入仓储，不依赖文件权限。

至少覆盖：

- 列表、名称搜索、技术栈搜索、状态筛选和三种排序；
- 新增成功、字段校验失败和 ID 自动生成；
- 编辑成功、保留 ID 和不存在 ID；
- 删除成功和不存在 ID；
- 非法 JSON、缺失字段、错误类型、非法 ID 和非法查询组合；
- 仓储保存失败映射为 `500`，且 ProjectManager 回滚规则保持成立；
- 服务可启动、可处理请求并可通过 `stop()` 结束。

## 分阶段实现边界

实现时按以下顺序拆分，并在每阶段先写失败测试：

1. **HTTP 依赖与共享构建目标**：加入 `cpp-httplib`、HTTP 库目标和最小服务器骨架；
2. **JSON 映射与错误响应**：实现请求校验、项目对象转换和稳定错误契约；
3. **查询路由**：实现列表、搜索、筛选和排序；
4. **写入路由**：实现新增、编辑、删除，并验证持久化失败不破坏内存状态；
5. **HTTP 入口和集成测试**：新增 `devmanager_http`、动态端口测试和 CI 验证；
6. **文档与发布检查**：更新 README、构建说明和 v0.3 版本信息。

每阶段完成标准为：目标范围内测试通过、未越过分层边界、现有 CLI 测试保持通过，并在 Windows 与 Ubuntu CI 上成功构建和运行测试。
