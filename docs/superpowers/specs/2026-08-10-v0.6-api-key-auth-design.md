# DevManager v0.6 API Key Authentication Design

状态：设计已批准，尚未开始编码。

目标版本：v0.6.0

## 1. 背景与目标

DevManager v0.5 已具备 CLI、HTTP API、JSON/SQLite 可配置存储、分页查询、OpenAPI 和 Windows/Ubuntu CI。本阶段只为 HTTP 服务增加单用户 API Key 认证，改善本地服务被未授权调用的风险。

目标是：

- 保持现有 Domain、ProjectManager、ProjectService、Repository 和数据库行为不变；
- 为 HTTP 业务接口增加统一认证边界；
- 保持 `/health` 公开，便于服务探活；
- 让认证失败具备稳定的 HTTP 错误契约、Request ID 和测试覆盖；
- 不引入用户系统或复杂安全基础设施。

## 2. 范围

### 2.1 包含

- 单用户、单 API Key；
- 从环境变量 `DEVMANAGER_API_KEY` 读取 API Key；
- 请求头格式 `Authorization: Bearer <API_KEY>`；
- HTTP 服务启动时读取并校验 API Key；
- `/api/info`、`/api/projects`、`/api/statistics` 认证；
- `/health` 公开；
- 统一 `401 unauthorized` 错误响应和 `WWW-Authenticate: Bearer` 响应头；
- 认证单元测试、HTTP 集成测试、CLI 回归测试；
- OpenAPI、README、GitHub Actions 和 v0.6 发布契约更新。

### 2.2 明确不包含

- JWT、OAuth2、Session、Refresh Token；
- 用户、角色、权限或密码系统；
- API Key 数据库存储、轮换 API 或多 Key；
- HTTPS/TLS、CORS、CSRF；
- CLI 认证；
- 数据库 schema 变化；
- 日志中记录 API Key；
- Docker、云部署、网关或反向代理。

## 3. 技术栈

| 领域 | 技术 | 约束 |
|---|---|---|
| 语言 | C++17 | 不升级语言标准 |
| HTTP | cpp-httplib | 复用现有 HTTP 生命周期和路由 |
| JSON | nlohmann/json | 复用现有错误响应 |
| 认证 | C++17 标准库 | 不引入 JWT 或密码学库 |
| 测试 | GoogleTest 1.17.0 | 先失败测试，再实现 |
| 持续集成 | GitHub Actions | Ubuntu + Windows，运行完整 CTest |
| 文档 | OpenAPI YAML、README | 与实际接口保持一致 |

## 4. 架构

```text
http_main
    ↓
ApplicationBootstrap
    ├── Config
    ├── Logger
    ├── EnvironmentApiKeyProvider
    ├── ApiKeyAuthenticator
    ├── ProjectRepository
    ├── ProjectManager
    └── ProjectService
          ↓
      HttpServer
          ├── /health                  公共
          ├── /api/info                认证
          ├── /api/projects            认证
          └── /api/statistics          认证
```

认证属于 HTTP/Application Infrastructure 边界，不进入 `Project`、`ProjectManager`、`ProjectService` 或任何 Repository。

### 4.1 EnvironmentApiKeyProvider

职责：

- 在 HTTP 启动阶段读取 `DEVMANAGER_API_KEY`；
- 拒绝变量缺失或值为空；
- 返回内存中的不透明非空字符串；
- 只读取一次，运行期间不重新读取环境变量。

环境变量值不自动 trim，按原字符串保存。HTTP 服务缺少有效 API Key 时启动失败并以非零状态退出。CLI 不创建或使用该 Provider。

### 4.2 ApiKeyAuthenticator

职责：

- 解析 `Authorization` Header；
- 严格接受 `Bearer <token>`；
- 拒绝缺失 Header、错误 scheme、空 token、额外 token、首尾多余空白和错误 key；
- 使用不提前返回的比较逻辑处理 key 比较；
- 不暴露配置值和实际 token。

scheme 区分大小写，只有 `Bearer` 合法。API Key 视为不透明非空字符串，不做大小写转换或 trim。

## 5. 请求流程和错误契约

```text
HTTP request
    ↓
确定是否为受保护路由
    ↓
读取 Authorization
    ↓
解析 Bearer <key>
    ↓
ApiKeyAuthenticator 校验
    ├── 失败 → 401 + WWW-Authenticate: Bearer
    └── 成功
          ↓
    ProjectHttpController
          ↓
    ProjectService
```

### 5.1 认证失败

所有认证失败使用相同的业务错误码和通用消息：

```json
{
  "error": {
    "code": "unauthorized",
    "message": "authentication required"
  }
}
```

响应要求：

- HTTP 状态码为 `401`；
- 包含 `WWW-Authenticate: Bearer`；
- 保留现有 `X-Request-ID` 行为；
- 不区分缺少 key、格式错误和 key 不匹配；
- 不返回实际 key、环境变量值或内部异常细节。

认证失败发生在 Controller 解析业务 JSON 或查询参数之前。认证成功后，原有 400、404、409、500 行为保持不变。

未知路由继续使用现有 404 行为；认证只对已定义的受保护接口生效。

### 5.2 日志边界

现有 HTTP 日志可以记录 method、path、status、duration 和 request ID。不得记录：

- `Authorization` Header；
- API Key；
- `DEVMANAGER_API_KEY` 的值；
- 包含 key 的异常文本。

认证成功或失败只允许记录不含敏感值的结果信息。

## 6. 测试与验收

### 6.1 单元测试

覆盖：

- Provider 读取存在、缺失和空环境变量；
- Provider 只在构造/启动时读取一次；
- 正确 Bearer Header；
- 缺失 Header；
- 非 Bearer scheme；
- 空 token；
- 额外空白或额外 token；
- 错误 key、前缀相同 key、不同长度 key；
- 认证比较不因首字符不匹配而提前返回；
- 401 错误结构和 `WWW-Authenticate`。

单元测试直接注入已知 key，不依赖开发机已有环境变量。

### 6.2 HTTP 集成测试

覆盖：

| 场景 | 预期 |
|---|---|
| HTTP 缺少 `DEVMANAGER_API_KEY` 启动 | 启动失败，非零退出 |
| 正确 key 访问 `/api/info` | 原有成功响应 |
| 正确 key 访问 `/api/projects` | 原有 CRUD、查询和分页行为 |
| 正确 key 访问 `/api/statistics` | 原有统计行为 |
| 无 key 或错误 key 访问受保护路由 | 401、固定错误结构、Bearer challenge |
| `/health` 无认证访问 | 200，返回 `{"status":"ok"}` |
| 认证失败带 `X-Request-ID` | 按现有规则返回 request ID |
| 正确 key 但业务参数非法 | 进入原有业务校验，不误判为认证失败 |
| CLI 启动和菜单操作 | 与 v0.5 一致，不读取 API Key |

### 6.3 完成标准

1. 缺少 API Key 时 HTTP 服务拒绝启动。
2. 受保护接口无合法 Bearer Key 时统一返回 401。
3. 合法 Key 不改变现有项目和统计功能。
4. `/health` 保持公开。
5. CLI 不受影响。
6. API Key 不进入 Domain、Repository、JSON、SQLite、响应或日志。
7. OpenAPI 与实际认证行为一致。
8. Ubuntu 和 Windows CI 均通过认证测试及完整 CTest。
9. C++17、cpp-httplib、nlohmann/json、GoogleTest 1.17.0 保持不变。

## 8. 开发阶段

### Phase 0：v0.5 基线检查

- 检查实际 HTTP 路由、Bootstrap、错误映射、Request ID 和现有 CI；
- 验收：确认设计与源码一致，不改代码。

### Phase 1：认证组件

- 先写 Provider/Authenticator 失败测试；
- 实现环境读取、Header 解析和安全比较；
- 验收：认证单元测试通过。

### Phase 2：HTTP 边界接入

- 先写受保护路由、401 和 challenge 测试；
- 将认证接入 HttpServer/ApplicationBootstrap；
- 验收：HTTP 集成测试通过，业务层接口未改变。

### Phase 3：回归和安全边界

- 完成 `/health`、Request ID、错误隐藏、CLI 回归和日志检查；
- 验收：认证、HTTP、CLI 和原有 CTest 全部通过。

### Phase 4：契约和 CI

- 更新 OpenAPI、README、版本说明和双平台 CI；
- 验收：OpenAPI validator、release contract、Ubuntu/Windows CTest 全部通过。

### Phase 5：发布

- 代码审查、完整构建和测试；
- 提交 v0.6 变更并准备 v0.6.0 发布记录；
- 不自动创建远程 Release，除非另行授权。

## 9. 设计风险与取舍

- C++17 标准库没有密码学级常量时间比较 API。本阶段使用不提前返回的比较逻辑，不引入额外密码学库；该方案适用于本地单用户 API Key，不宣称等同于专业密码学实现。
- 环境变量在启动时读取一次，运行期间修改环境变量不会改变认证结果，这是为了保证请求行为稳定。
- 启用认证后，旧的无认证 HTTP 客户端访问业务接口会得到 401，这是 v0.6 的明确兼容性变化；`/health` 不受影响。
- 测试使用注入 key 和隔离进程/环境，避免依赖开发机环境或污染真实配置。

## 10. 技术和范围结论

v0.6 只完成 HTTP 单用户 API Key 认证。它不会扩展为用户系统，也不会改变 v0.5 的存储、查询、分页、统计或 CLI 架构。实现必须遵循“先失败测试，再最小实现，再完整回归验证”的顺序。
