# DevManager v0.7 Service Reliability Design

状态：设计修订完成，尚未开始编码。

目标版本：v0.7.0

## 1. 目标

在 v0.6 API Key 认证的基础上，增强本地单进程 HTTP 服务的生命周期可靠性：

- 增加可区分的就绪状态；
- 支持 Windows/Linux 的优雅停止；
- 限制 HTTP 请求体大小；
- 保持现有业务 API、认证、分页、错误 JSON 和存储行为兼容。

本版本仍定位为本地单进程服务，不引入 Docker、Kubernetes、systemd、Windows Service、服务注册中心或外部进程管理器。

| 模块 | 技术 |

## 3. 明确不包含

v0.7 不实现：

- Docker、Kubernetes、systemd、Windows Service；
- 多进程部署、服务发现、负载均衡；
- 数据库连接池、Redis、消息队列；
- 用户系统、JWT、OAuth、权限模型；
- WebSocket、文件上传和前端页面；
- HTTP API 的 CRUD、查询、分页或认证语义重设计。

## 4. 生命周期状态

\`\`\`text
Starting
   |
   | 配置、Repository、路由初始化完成
   v
Ready
   |
   | SIGINT / SIGTERM / Windows Ctrl+C
   v
Stopping
   |
   | 停止监听并等待活动请求
   v
Stopped
\`\`\`

异常路径：

\`\`\`text
Starting -> Failed
Ready    -> Failed
\`\`\`

| 状态 | \`/health\` | \`/ready\` |
|---|---:|---:|
| Starting | 200 | 503 |
| Ready | 200 | 200 |
| Stopping | 200 | 503 |
| Stopped | 不再提供 | 不再提供 |
| Failed | 进程退出 | 进程退出 |

\`/health\` 继续表示 HTTP 进程存活，不检查 Repository、数据库或 migration。\`/ready\` 表示服务已完成配置、Repository、SQLite migration、路由和认证初始化。两个接口都不需要 API Key。

\`/ready\` 的成功响应固定为 HTTP 200 和 \`{\"status\":\"ready\"}\`；Starting 或 Stopping 时固定返回 HTTP 503 和现有错误 JSON \`{\"error\":{\"code\":\"not_ready\",\"message\":\"service is not ready\"}}\`。两种响应都必须带现有 \`X-Request-ID\`。

初始化失败必须在进入 Ready 前退出，不允许以半初始化状态继续监听。

## 5. 分层架构

\`\`\`text
http_main
    |
ServiceLifecycle
    +-- SignalHandler
    +-- ReadinessState
    +-- StopRequestSource (application port)
    +-- ServiceRuntime (application port)
            ^
            |
        HttpServer
            |
      ProjectHttpController
            |
      ProjectService
            |
      ProjectRepository
\`\`\`

### ReadinessState

职责：

- 保存生命周期状态；
- 使用 \`std::atomic\` 或等价线程安全实现；
- 提供 \`markReady()\`、\`markStopping()\`、\`markStopped()\`、\`markFailed()\`、\`isReady()\`；
- \`markReady()\` 只允许 \`Starting -> Ready\`；\`Stopping\` 不得重新变为 Ready；\`Stopped\` 与 \`Failed\` 是终态，后续标记不得把它们改回其他状态；
- 不创建业务对象，不操作 HTTP 请求，不写 Repository。

### SignalHandler

职责：

- Linux 注册 \`SIGINT\`、\`SIGTERM\`；
- Windows 注册 Ctrl+C 对应处理；
- 第一次信号只设置 stopRequested；第二次及后续停止信号设置 forceStopRequested；
- 信号回调只执行异步信号安全的标志写入，使用 std::sig_atomic_t 或已验证无锁的原子类型；
- 信号回调不得执行日志、锁或条件变量通知、内存分配、Repository 操作、HTTP 调用、对象清理或线程终止；
- 提供线程安全的停止请求读取或等待接口。

### ServiceLifecycle

职责：

- 协调 \`HttpServer\`、\`ReadinessState\` 和 \`SignalHandler\`；
- 初始化完成后标记 Ready；
- 收到停止请求后标记 Stopping；
- 调用 \`HttpServer::stop()\` 停止接收新请求；
- 等待活动请求结束，使用 5 秒 drain deadline；
- 观察到 forceStopRequested 时跳过剩余等待并进入失败退出结果路径；
- 记录停止原因、强制停止请求和超时；
- 最终标记 Stopped，并返回明确的退出结果；未收到停止请求时返回 NoStopRequested，不得伪装为已停止。

初始化或运行过程发生未处理异常时，ServiceLifecycle 必须先标记 Failed，再向入口返回失败结果。

ServiceLifecycle 不包含项目业务规则、HTTP JSON 解析、认证规则或 SQL。

为保持 Application 层不依赖 cpp-httplib，ServiceLifecycle 只依赖应用层的 `StopRequestSource` 和 `ServiceRuntime` 端口；HttpServer 在 HTTP 层实现 `ServiceRuntime`，SignalHandler 在 infrastructure/runtime 层实现 `StopRequestSource`。这两个端口只包含生命周期所需的最小方法，不泄漏 HTTP 请求、响应或 OS 信号类型。

### HttpServer

保留现有职责：

- 路由注册、监听和停止；
- API Key 认证边界；
- Request ID；
- HTTP 错误映射。

v0.7 新增：

- 注入或读取 \`ReadinessState\`；
- 注册 \`/ready\`；
- 使用 cpp-httplib 的 \`Server::set_payload_max_length\` 设置 1 MiB 上限。

## 6. 请求体限制

所有 HTTP 请求体的上限固定为：

\`\`\`text
1 MiB = 1024 * 1024 bytes
\`\`\`

规则：

- 当前 DevManager 实际携带业务请求体的接口是 \`POST\`、\`PUT\`；
- \`GET\`、\`DELETE\` 通常不携带业务请求体，因此其现有无请求体行为不变；本版本不承诺带请求体的 \`DELETE\` 绕过全局上限；
- 超过上限在 JSON 解析和 ProjectService 调用之前拒绝；
- 返回 HTTP \`413 Payload Too Large\`；
- 错误码为 \`payload_too_large\`；
- 不新增配置字段；
- \`/health\` 和 \`/ready\` 的响应不受该业务请求体契约影响。

优先使用当前 cpp-httplib 已提供的 \`Server::set_payload_max_length(size_t)\`，不自行读取原始 socket，也不修改第三方库默认宏。

## 7. 优雅停止

- Linux：处理 \`SIGINT\`、\`SIGTERM\`；
- Windows：处理 Ctrl+C 对应的 \`SIGINT\`；
- 第一次信号启动优雅停止；
- 第二次及后续信号只设置 forceStopRequested；ServiceLifecycle 在线程协调点观察到该标志后，跳过剩余 drain 等待并进入失败退出结果路径；信号回调本身不立即终止进程、不清理 C++ 对象，也不强制杀线程；
- 停止过程中不得把 API Key 或 Authorization 写入日志。

停止流程：

\`\`\`text
收到停止信号
  |
SignalHandler 设置 stopRequested
  |
ServiceLifecycle 标记 Stopping
  |
HttpServer::stop()
  |
停止接收新连接并开始 drain
  |
观察 forceStopRequested？——是——> 跳过剩余等待，记录失败退出结果
   |
   否
   |
5 秒 drain deadline 内完成：正常退出
5 秒超时：记录 shutdown_timeout，标记失败结果
   |
安全等待 cpp-httplib 工作线程结束后再销毁对象
\`\`\`

C++ 标准库和 cpp-httplib 默认线程模型不能安全地强制终止卡住的线程。因此，5 秒定义为停止协调的 drain deadline，而不是保证进程在第 5 秒消失的硬退出 deadline：服务应停止监听新连接；在 deadline 内完成则返回成功，超时则记录 shutdown_timeout 并将最终退出结果标记为失败；无论是否超时，都必须在安全销毁 C++ 对象前等待并 join cpp-httplib 工作线程。v0.7 不使用未定义行为、强制杀线程或泄漏 joinable 线程，也不承诺卡住业务线程能在 5 秒内被强制终止。

\`\`\`text

## 9. 测试矩阵

### ReadinessState 单元测试

- 初始状态为 Starting；
- \`markReady()\` 后为 Ready；
- \`markStopping()\` 后不再 Ready；
- \`markStopped()\` 后状态稳定；
- 并发读取状态不会产生数据竞争。

### SignalHandler 和 ServiceLifecycle 测试

- 第一次停止请求只执行一次停止流程；
- 第二次停止请求只设置 forceStopRequested，由生命周期协调器观察后进入失败退出结果路径；
- 信号回调不直接调用日志、锁、条件变量、Repository、HTTP 或业务对象；
- 初始化失败不会标记 Ready；
- 停止流程会调用 server stop；
- 活动请求在超时前完成时正常退出；
- 超过 5 秒时记录 shutdown_timeout、返回失败结果，并安全等待工作线程结束。

生命周期测试应使用可注入的 fake runtime/clock 或等价测试适配器，不依赖真实 OS 信号时序制造全部失败场景。

### HTTP 集成测试

- \`/health\` 无 API Key 返回 200；
- \`/ready\` 在 Starting/Stopping 返回 503；
- \`/ready\` 在 Ready 返回 200；
- \`/ready\` 不需要 API Key；
- 请求体恰好 1 MiB 不被拒绝；
- 超过 1 MiB 返回 413 和 \`payload_too_large\`；
- 超大 JSON 不进入 ProjectService；
- 停止后不再接受新业务请求；
- 既有认证、CRUD、查询、分页、统计和日志测试继续通过。

## 11. 风险与设计取舍

- \`std::signal\` 和 Windows Console Handler 的可测试性不同，必须通过可注入停止源或 fake runtime 降低时序测试脆弱性；
- cpp-httplib 的 \`stop()\` 负责关闭监听 socket，但不应被假设为强制终止所有业务线程；
- 5 秒是 drain deadline 和退出结果判定边界，不是硬性进程终止 deadline；超时只允许记录、返回失败结果和安全清理，不允许强制杀线程；
- 第二次信号只能设置安全的强制停止标志，不能在信号回调中执行立即退出、日志、锁、内存分配或对象清理；
- \`/ready\` 不需要 API Key，避免探针因认证配置失败而无法判断服务状态；
- 全局 HTTP request body limit 固定为 1 MiB，不扩展 Config，降低 v0.7 的配置兼容风险；
- 版本升级到 v0.7.0 只在 Phase 4 统一进行，避免实现中间状态出现版本不一致。

## 13. 范围结论

v0.7 只增强本地单进程 HTTP 服务可靠性，不改变现有业务架构。所有实现必须遵守：先写失败测试，再做最小实现，再运行完整回归；不得提前加入数据库以外的存储、容器、服务编排或前端功能。
