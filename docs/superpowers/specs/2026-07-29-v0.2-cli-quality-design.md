# DevManager v0.2 CLI Quality Design

**Goal:** Improve the released command-line DevManager without adding HTTP, database, Redis, Docker, frontend, or other v0.3 scope.

## Architecture

The current layer direction remains unchanged:

```text
MenuController -> ProjectManager -> ProjectRepository -> JsonProjectRepository
```

`MenuController` owns prompts, parsing, retries and rendering. `ProjectManager` owns edit, filtering, sorting, ID rules and mutation orchestration. `JsonProjectRepository` owns JSON parsing and file I/O. `ProjectManager` must not include JSON headers, open files or parse user input.

`ProjectRepository` exposes `loadStore()` and `saveStore(const ProjectStore&)`; both methods use `ProjectStore` as their sole persistence boundary. For every persisted mutation, `ProjectManager` creates a candidate `ProjectStore`, asks the repository to `saveStore` it, then replaces its in-memory state only when the save succeeds. A failed save leaves the in-memory project list and `nextId` unchanged.

`AsciiText` is a pure utility component shared by the menu and business layers. It provides ASCII-only surrounding-whitespace trimming and ASCII lowercase normalization. It does not parse commands or IDs: full-line input parsing remains the responsibility of `MenuController`.

## Functional Scope

### Edit project

- Edit targets an existing positive ID.
- The project retains its original ID.
- The menu displays the existing project, then asks for all fields again: name, comma-separated technology tags, description and status.
- Description may be empty and means clear the description.
- Blank name, blank status, no tags or blank tags are rejected by existing `Project` validation.
- A missing ID reports a clear error and returns to the menu.

### Filter by status

- Filter is ASCII-case-insensitive exact matching after surrounding ASCII whitespace is trimmed.
- It returns a project copy list and does not change stored insertion order.
- An empty status query returns no results and prints the existing empty-result message.

### Sort projects

- Support sort key `id`, `name`, or `status`.
- All sorts are ascending in v0.2.
- Name and status compare ASCII-case-insensitively; equal values use ID ascending as a deterministic tie-breaker.
- Sorting returns a copy and does not reorder the persisted project vector.

## Persistence and Error Behavior

- A missing JSON file starts a new empty store with `nextId == 1`. An empty store created by deleting all projects retains its forward `nextId`, so IDs are never reused after a restart.
- A corrupt, semantically invalid, unreadable or unwritable file produces a repository error with the file path.
- Valid snapshots require `nextId >= 1`, positive and unique project IDs, and—when projects exist—`nextId` greater than every stored ID. IDs are never reused, including after deletion.
- If `nextId == UINT64_MAX`, `ProjectManager` rejects a new-project request before creating a candidate store. It does not modify memory or write a file.
- Saving writes a temporary file in the target directory, verifies its write and close results, then asks a repository-only file-replacement adapter to safely replace the target. The adapter uses an OS-aware replacement strategy on Windows and `rename`-style replacement on POSIX systems. C++17 `std::filesystem::rename` does not guarantee an atomic overwrite replacement on Windows, so it must not be relied upon for that operation. A failed save preserves the original JSON file and the manager's in-memory state.
- The menu catches save errors for add, edit and delete, prints an operation failure message and stays usable with the old in-memory state.
- A load error occurs before the menu starts, so `main` prints the error and returns a non-zero status.

## Menu Input Behavior

- Commands use full-line parsing.
- Unknown command, blank command, non-numeric ID, zero, signed ID and overflowing ID are invalid input.
- Invalid values re-prompt the current command where appropriate; EOF exits cleanly.
- A valid but absent project ID reports `Project ID not found` and does not request mutation confirmation.
- Delete accepts `y` or `Y`; every other confirmation cancels deletion.

## Testing

- Migrate hand-written test executables to GoogleTest v1.17.0 through CMake `FetchContent`.
- Use fixtures with unique temporary directories for repository and integration tests.
- Cover edit success/validation/missing-ID, status filtering, every sort key and tie-breaker, invalid menu inputs, missing IDs, corrupt/missing JSON, snapshot validation, `nextId` overflow, and ProjectManager rollback on save failure.
- Retain end-to-end menu tests with injected streams and a fake `ProjectRepository` that can deliberately fail `saveStore`.
- Repository save-failure tests inject a failing file-replacement or file-operations adapter. They do not depend on host file permissions.

## Continuous Integration

- Add `.github/workflows/ci.yml`.
- Run on pushes and pull requests.
- Build and test on `ubuntu-latest` and `windows-latest`.
- Configure with CMake, build Debug, then run `ctest --test-dir build -C Debug --output-on-failure` on both platforms.

## Explicit Non-Goals

- No HTTP service, REST API, database, MySQL, Redis, Docker, browser UI or frontend.
- No user accounts, authentication, concurrent editing, import/export or project deletion recovery.
- No descending sort order, pagination, fuzzy search, migration tool, logging system or configuration subsystem.
