# DevManager v0.9 Docker Compose Deployment Design

状态：设计阶段，尚未开始编码。

目标版本：v0.9.0

## 1. 目标

将已发布的 DevManager v0.8 HTTP 服务封装为可重复构建、可在本机 Docker Compose 中启动的单容器服务。部署版保留现有 API Key、SQLite、`/health`、`/ready`、优雅停止和错误 JSON 契约。

本版本的完成定义是：从干净的仓库检出和一份未提交的本地环境文件开始，执行一个 Compose 命令即可构建、启动、检查就绪状态，并在重启后保留 SQLite 数据。

## 2. 技术栈

| 模块 | 技术 |
| --- | --- |
| 服务 | C++17、CMake、cpp-httplib、SQLite |
| 构建镜像 | Docker 多阶段构建、Debian Linux 基础镜像 |
| 本地编排 | Docker Compose v2 |
| 配置与密钥 | JSON 配置文件、`DEVMANAGER_API_KEY` 环境变量、本地 `.env` |
| 持久化 | Docker named volumes |
| 验证 | CTest、Docker Compose、HTTP smoke test、GitHub Actions Ubuntu + Windows |

## 3. 范围

新增：

- 多阶段 `Dockerfile`，在 builder 阶段构建并测试 `devmanager_http`，在 runtime 阶段仅运行产物及运行时依赖；
- `deploy/docker/compose.yaml` 单服务编排；
- 容器专用 JSON 配置，监听容器内的 `0.0.0.0:8080`；
- SQLite 数据、文件日志的 named volumes；
- `.env.example`、`.dockerignore`、部署说明；
- Ubuntu CI 中的 Compose build/start/ready/auth/persistence smoke test。

不新增：

- 新 HTTP 路由、业务能力、Repository 或领域模型改动；
- Nginx、TLS、反向代理、Redis、消息队列、第二个数据库服务；
- Docker Swarm、Kubernetes、云部署、镜像仓库推送或自动发布容器镜像；
- API Key 轮换、Docker secrets 管理服务或对外公网暴露。

## 4. 部署架构

```text
host browser / curl
        |
127.0.0.1:${DEVMANAGER_PORT}
        |
Docker Compose
        |
devmanager container (non-root)
  |- devmanager_http :8080
  |- config/devmanager.json (read-only image content)
  |- /var/lib/devmanager  <- named volume: devmanager-data
  `- /var/log/devmanager  <- named volume: devmanager-logs
```

Compose 只声明一个 `devmanager` 服务。SQLite 继续是进程内嵌存储，不把 SQLite 拆成网络数据库服务。

## 5. 容器构建

### 5.1 Dockerfile

使用命名的 `builder` 和 `runtime` 两个阶段。所有基础镜像在实施时固定为明确的 Debian Bookworm digest；禁止使用 `latest`。

`builder` 阶段：

1. 安装 `build-essential`、CMake、Ninja、Git、CA certificates；
2. 复制由 `.dockerignore` 缩小后的源码；
3. 以 `Release` 配置 CMake；
4. 构建 `DevManagerHttpServer`，运行完整 CTest；
5. 将 `devmanager_http` 交给 runtime 阶段。

`runtime` 阶段：

- 安装二进制所需的动态运行时库和 `curl`；
- 创建固定的非 root 用户（UID/GID `10001`）；
- 复制 HTTP 可执行文件和容器配置；
- 创建并授权 `/var/lib/devmanager`、`/var/log/devmanager`；
- 使用 `ENTRYPOINT ["/opt/devmanager/devmanager_http"]`。

镜像构建不能读取工作树中的构建目录、`logs/`、SQLite 数据库、本地 `.env` 或 Git 历史。

### 5.2 Docker ignore

`.dockerignore` 至少排除 `.git/`、`.worktrees/`、`build*/`、`logs/`、`data/`、本地 `.env` 文件、Python cache 和测试生成物。它不排除 `database/migrations/`、`cmake/`、`include/`、`src/`、`config/` 等构建输入。

## 6. Compose 契约

`deploy/docker/compose.yaml` 使用下列固定行为：

- `build.context` 指向仓库根目录，镜像名带 `0.9.0`；
- `DEVMANAGER_API_KEY` 必须从 `deploy/docker/.env` 插值提供，缺失时 Compose 在启动前失败；
- `.env.example` 中的 `DEVMANAGER_PORT=8080` 映射为 `127.0.0.1:8080:8080`；将变量留空时 Docker 分配随机 loopback host 端口，仍不暴露到局域网或公网；
- `restart: unless-stopped`；
- `init: true`；
- `stop_grace_period: 10s`，给 v0.7 的 drain deadline 留出额外的容器协调余量；
- 容器以非 root 用户执行，并使用 `read_only: true`、`cap_drop: [ALL]`、`no-new-privileges:true`；唯一可写路径是两个 volume 与 `/tmp` tmpfs；
- `healthcheck` 访问容器内 `http://127.0.0.1:8080/ready`；`/ready` 为 200 才标记 healthy。

标准启动命令固定为：

```powershell
docker compose --env-file deploy/docker/.env -f deploy/docker/compose.yaml up -d --build
```

显式传入 `--env-file`，避免调用目录变化时误读取其他 `.env` 文件；停止与保留数据使用同一 Compose 文件的 `docker compose ... down`。

`DEVMANAGER_API_KEY` 不能写进 `compose.yaml`、镜像层、配置 JSON、README 示例命令的历史记录或 Git。`.env.example` 只包含占位值说明，真实 `.env` 必须被 Git 忽略。

Docker 官方文档更推荐用 secrets 传递敏感值。当前程序只支持从环境变量读取 API Key，v0.9 为了不引入第二套密钥读取机制，明确把被 Git 忽略、仅限本机的 `.env` 作为开发部署折中；它不等同于生产密钥管理。Docker secrets 文件读取支持应作为未来独立版本设计，而不能在本版本偷偷加入。

## 7. 容器配置与数据语义

新增 `deploy/docker/config/devmanager.json`：

```json
{
  "server": { "host": "0.0.0.0", "port": 8080 },
  "storage": { "type": "sqlite", "path": "/var/lib/devmanager/devmanager.db" },
  "logging": { "level": "info", "path": "/var/log/devmanager/devmanager.log" }
}
```

容器启动仍由现有 `http_main` 依次加载配置、读取 API Key、构建 Repository 和 SQLite migration、启动监听、进入 Ready。API Key 缺失或 SQLite migration 失败必须非零退出，健康检查不会伪装为 healthy。

`docker compose down` 不带 `-v` 时保留 SQLite 和日志卷；`docker compose down -v` 才是明确的数据删除操作，文档必须标出此风险。

## 8. 生命周期与网络

Compose 通过 `SIGTERM` 停止 Linux 容器。现有 v0.7/v0.8 生命周期代码负责停止监听、drain 已开始的请求并安全 join；Compose 只提供 10 秒宽限期，不实现强杀或 detach。

Docker health check 使用公开 `/ready`，不需要 API Key。所有 `/api/*` 业务路由继续要求 `Authorization: Bearer <DEVMANAGER_API_KEY>`；`/health` 与 `/ready` 保持公开。

容器内绑定 `0.0.0.0` 是 Compose 端口转发所需，不代表 host 对公网开放；host 的 `127.0.0.1` 端口映射才是本地默认安全边界。若未来需要 LAN 或公网访问，必须作为独立版本设计 TLS/反向代理和认证边界，v0.9 不提供开关。

## 9. 验证策略

先失败测试或验证，再最小实现。必须覆盖：

| 场景 | 验收 |
| --- | --- |
| Compose 配置 | `docker compose config` 成功；缺少 `.env` key 时在启动前明确失败 |
| 镜像 | 多阶段 build 成功；最终镜像不含 builder、源码、真实 key 或本地数据 |
| 就绪 | `docker compose up -d --build` 后 `/health`、`/ready` 返回 200，服务为 healthy |
| 认证 | 未认证 `/api/projects` 为 401；正确 Bearer key 可调用已有项目列表 |
| 持久化 | 创建项目后 `docker compose restart`，同一项目仍可读取 |
| 停止 | `docker compose stop` 正常退出，日志不包含 API Key |
| 回归 | CTest 全量通过；OpenAPI 和 release contract validator 继续通过 |

Ubuntu GitHub Actions 新增 Docker job，执行 build、Compose 启动、ready/auth/persistence smoke、日志脱敏检查和 `docker compose down -v` 清理。Windows 和 Ubuntu 的既有 CTest job 保持不变；Windows CI 不依赖 Docker Desktop。

## 10. 文件边界

```text
Dockerfile                              # 镜像构建，不含业务代码
.dockerignore                           # 构建上下文边界
deploy/docker/compose.yaml              # 单服务本地编排
deploy/docker/.env.example              # 无真实值的必需环境变量说明
deploy/docker/config/devmanager.json    # 容器运行配置
scripts/check_docker_compose.py         # 可重复的 Compose smoke 验证
.github/workflows/ci.yml                # Ubuntu Docker job
README.md                                # 本地部署与数据删除警告
tests/deployment/...                    # 仅在适合 CTest 的纯文件契约检查存在时使用
```

除部署配置和验证需要外，不修改 `Project`、`ProjectManager`、`ProjectService`、Repository、HTTP controller、API Key 或生命周期实现。

## 11. 风险与决定

| 风险 | 决定 |
| --- | --- |
| Docker base tag 漂移 | 实施时固定 digest，并在 README 记录来源 |
| API Key 泄漏 | 只从被忽略的 `.env` 注入；日志/配置/镜像层均禁止包含 key |
| SQLite 数据误删 | 默认 named volume；文档明确 `down -v` 会删除数据 |
| 端口意外暴露 | 默认固定 127.0.0.1；不提供 0.0.0.0 host override |
| 容器停止过早被杀 | 10 秒 Compose 宽限期，复用 v0.7/v0.8 drain 行为 |
| CI 与本机 Docker 差异 | Ubuntu CI 用 Docker Engine 验证 Compose；Windows 继续验证 C++ 构建与测试 |

## 12. 完成标准

v0.9.0 只有在以下条件均满足时才能发布：Dockerfile 和 Compose 均通过结构检查；Ubuntu Docker CI 与 Windows/Ubuntu CTest 通过；本地 Docker Desktop 完成一次真实 build、ready、认证、SQLite 重启持久化和优雅停止验证；README 不要求提交真实 API Key；不引入超出范围的服务或业务功能。
