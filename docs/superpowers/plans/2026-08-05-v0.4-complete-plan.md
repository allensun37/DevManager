# DevManager v0.4 Complete Implementation Plan

> **For agentic workers:** Execute task-by-task with test-first development. Keep the existing domain and repository boundaries intact.

**Goal:** Complete the approved v0.4 service enhancement without adding database, authentication, Docker, frontend, or unrelated infrastructure.

**Architecture:** Bootstrap owns runtime objects. ProjectService is the application boundary for HTTP use cases and owns the single project-state mutex. Logger is an infrastructure adapter; Domain and ProjectManager do not depend on spdlog. HTTP concerns stay in HttpServer/Controller/JSON mapping.

**Tech Stack:** C++17, CMake, nlohmann/json 3.12.0, cpp-httplib, GoogleTest 1.17.0, pinned spdlog, OpenAPI YAML validation in CI.

---

### Task 1: ProjectService and HTTP migration

Create `include/application/ProjectService.h`, `src/application/ProjectService.cpp`, and service tests. Expose CRUD/query operations as value-returning methods, a statistics DTO, and a single mutex around ProjectManager operations. Update `ProjectHttpController` and its tests to depend on ProjectService, update `HttpServer` construction, and update ApplicationBootstrap to own the service. Preserve all existing HTTP status/error contracts and CLI use of ProjectManager. First add failing service/controller tests, then implement, then run the full CTest suite.

### Task 2: Logger adapter

Pin spdlog in CMake. Add `include/infrastructure/logging/Logger.h`, `src/infrastructure/logging/Logger.cpp`, and focused tests using a temporary directory or memory sink. Bootstrap creates the logger; HTTP lifecycle and request handling log through it. Domain, ProjectManager, ProjectService, and repository interfaces must not include spdlog. Add failure-safe directory creation and stable message fields without exposing internal exceptions to clients.

### Task 3: Runtime configuration and HTTP enhancements

Wire `ConfigLoader("config/devmanager.json")` and ApplicationBootstrap into both entrypoints while preserving missing-config defaults. Add `/health`, `/api/info`, and `/api/statistics`. Use the generated CMake version for `/api/info`. Add request-ID validation/generation and response propagation for successful, 404, and error responses. Add focused HTTP and statistics tests before implementation. Keep statistics normalization independent from search normalization and count duplicate technology labels once per project.

### Task 4: OpenAPI contract

Create `docs/openapi.yaml` covering every existing and new endpoint, request/response JSON fields, status/error responses, query exclusivity, sorting, and `X-Request-ID`. Add a fixed-version YAML/OpenAPI validation step to GitHub Actions and a local validation command. Do not generate runtime code from the document.

### Task 5: Final integration and release preparation

Update README with CLI/HTTP/config/run/test instructions and v0.4.0 version source. Run clean CMake configure/build and CTest on the current toolchain, inspect `git diff --check`, verify no out-of-scope technology was added, update the workflow for Ubuntu and Windows, and create a local `v0.4.0` tag only after all checks pass. Do not push or create an external release without explicit authorization.
