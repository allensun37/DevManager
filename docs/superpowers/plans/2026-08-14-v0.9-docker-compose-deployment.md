# DevManager v0.9 Docker Compose Deployment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Package the existing v0.8 HTTP executable as a reproducible, locally loopback-only Docker Compose service with persistent SQLite data and verified readiness, authentication, restart, and shutdown behavior.

**Architecture:** A multi-stage Debian image builds and tests the existing C++17 project, then copies only `devmanager_http` plus its container configuration into a non-root runtime stage. Compose injects the existing API key through a Git-ignored local environment file, binds the host port to loopback, and mounts separate named volumes for SQLite and file logs. No Domain, application, repository, controller, authentication, or lifecycle behavior changes.

**Tech Stack:** C++17, CMake, CTest, Docker Engine, Docker Compose v5-compatible syntax, Debian Bookworm, Python 3 standard library smoke checks, GitHub Actions Ubuntu and Windows.

---

## Planned file structure

| Path | Responsibility |
| --- | --- |
| `Dockerfile` | Pinned multi-stage build/test/runtime image for `devmanager_http`. |
| `.dockerignore` | Keeps local builds, data, logs, Git history and secret files out of the build context. |
| `deploy/docker/compose.yaml` | One hardened, loopback-only `devmanager` service and its named volumes. |

| `.github/workflows/ci.yml` | Adds an Ubuntu-only Docker Compose job while retaining current Windows/Ubuntu CTest jobs. |
| `README.md` | Local deployment, data-retention, startup and cleanup instructions. |
| `scripts/validate_release_contract.py` | Locks the v0.9 version and documentation/deployment markers. |
| `CMakeLists.txt`, `docs/openapi.yaml`, `tests/common/DevManagerVersionTests.cpp` | Single-source v0.9 release version and matching version assertions. |

- [ ] **Step 3: Implement `deploy/docker/compose.yaml`**

Use this service-level shape:

```yaml
services:
  devmanager:
    image: devmanager:0.9.0
    build:
      context: ../..
      dockerfile: Dockerfile
    environment:
      DEVMANAGER_API_KEY: ${DEVMANAGER_API_KEY:?Set DEVMANAGER_API_KEY in deploy/docker/.env}
    ports:
      - "127.0.0.1:${DEVMANAGER_PORT}:8080"
    volumes:
      - devmanager-data:/var/lib/devmanager
      - devmanager-logs:/var/log/devmanager
    read_only: true
    tmpfs:
      - /tmp
    user: "10001:10001"
    cap_drop: [ALL]
    security_opt: [no-new-privileges:true]
    init: true
    restart: unless-stopped
    stop_grace_period: 10s
```

Add a curl-based `/ready` healthcheck with bounded interval, timeout, retries, and start period. Define the two named volumes after `services`.
