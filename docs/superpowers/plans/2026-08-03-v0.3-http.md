# DevManager v0.3 HTTP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a local, C++17 REST/JSON HTTP API for the existing v0.2 project-management capabilities while preserving the CLI and all existing layer boundaries.

**Architecture:** Add an HTTP adapter layer containing `HttpServer`, `ProjectHttpController`, `ProjectHttpJsonMapper`, and HTTP-only error construction. Both the existing CLI and the new HTTP executable share `ProjectManager` and `ProjectRepository`; `ProjectManager` remains unaware of HTTP and JSON request formats. All HTTP calls into the mutable manager are serialized at the HTTP boundary.

**Tech Stack:** C++17, CMake 3.20+, cpp-httplib pinned to commit `095a5c1caf9e467ff840ee2ffd19be1a7852203b`, nlohmann/json 3.12.0, GoogleTest 1.17.0, Ubuntu and Windows GitHub Actions.

- [ ] **Step 3: Implement the lifecycle and route boundary**

`HttpServer` must expose this stable interface:

```cpp
class HttpServer final {
public:
    HttpServer(ProjectManager& manager, std::string host, std::uint16_t port);

    void bind();
    void run();
    void stop() noexcept;
    [[nodiscard]] std::uint16_t boundPort() const noexcept;
};
```

`bind()` registers routes, binds the configured host, uses an ephemeral port when the requested port is `0`, and throws a descriptive exception when binding fails. `run()` calls the blocking listen-after-bind operation. `stop()` is safe to call after a successful bind. The executable uses `127.0.0.1` and `8080`; tests use `127.0.0.1` and `0`.

`ProjectHttpController` must expose only:

```cpp
class ProjectHttpController final {
public:
    explicit ProjectHttpController(ProjectManager& manager);
    void registerRoutes(httplib::Server& server);
};
```

Register the four routes from the design document. Protect every call that reads or mutates `ProjectManager` with a Controller-owned `std::mutex`. Copy project results while holding the lock, then serialize the copies. Do not add a mutex or HTTP include to `ProjectManager`.

The controller must map `ProjectManager` results and exceptions as follows:

- `false` from update/delete → `404 project_not_found`;
- `std::invalid_argument` from project input → `400 invalid_request`;
- shared ID parser failure → `400 invalid_id`;
- `std::overflow_error` from add → `409 id_exhausted`;
- repository/runtime failure → `500 persistence_failure`;
- JSON parse failure → `400 invalid_json`;
- unexpected exceptions → `500 internal_error`.

Add the two HTTP test targets and link them to `DevManagerHttp`, `GTest::gtest_main`, and the platform thread library only if the selected generator requires it.
