> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add readiness, graceful lifecycle coordination, and a 1 MiB request-body limit to local `devmanager_http` without changing v0.6 business, authentication, persistence, or CLI behavior.

**Architecture:** Application owns `ReadinessState`, `StopRequestSource`, `ServiceRuntime`, and `ServiceLifecycle`. Infrastructure `SignalHandler` implements the stop source; HTTP `HttpServer` implements the runtime and reads readiness for `/ready`. Application code must not include cpp-httplib, request/response, or operating-system signal types.

**Tech Stack:** C++17, CMake, cpp-httplib, nlohmann/json, GoogleTest 1.17.0, spdlog, SQLite/JSON Repository, GitHub Actions Ubuntu and Windows.

## Fixed contracts

`ServiceState` values are `Starting`, `Ready`, `Stopping`, `Stopped`, and `Failed`. `ReadinessState` starts as `Starting`; only `Ready` makes `isReady()` true. `markReady()` only permits `Starting -> Ready`, so `Stopping` cannot return to Ready. `Stopped` and `Failed` are terminal and cannot be overwritten by later markers. It exposes `state()`, `isReady()`, `markReady()`, `markStopping()`, `markStopped()`, and `markFailed()` and stores state atomically.

`StopRequestSource` exposes `stopRequested()` and `forceStopRequested()`. `ServiceRuntime` exposes `stopAccepting()` and `waitUntilDrained(std::chrono::milliseconds)`. `ServiceLifecycle` depends only on these application ports, `ReadinessState`, and existing `Logger`.

First stop marks Stopping and calls `stopAccepting()` exactly once. A second stop only sets force-stop state and skips remaining drain work. No stop request returns `NoStopRequested`, not `Stopped`. A 5-second drain deadline decides the exit result: timeout logs `shutdown_timeout` and returns failure, but object destruction still waits for cpp-httplib workers to end safely. No forced thread termination and no five-second hard-process-exit promise.

`GET /ready` is public. Ready returns `200 {"status":"ready"}`. Starting and Stopping return `503 {"error":{"code":"not_ready","message":"service is not ready"}}`. Every response includes `X-Request-ID`. `/health` remains public `200 {"status":"ok"}` and does not check readiness or storage.

`HttpServer` calls `server_.set_payload_max_length(1024U * 1024U)`. This is a global request-body limit. Current business body endpoints are POST and PUT. Oversize input returns JSON `413 payload_too_large` with `X-Request-ID` before JSON parsing or ProjectService calls.

`SignalHandler` implements `StopRequestSource`. - [x] **Step 3: Implement runtime adaptation and startup order**

`HttpServer::stopAccepting()` delegates to existing `stop()`. Its concrete drain behavior waits for and safely joins the dedicated thread that runs `listen_after_bind()`; it never detaches. The existing synchronous `run()` remains for direct test use. `http_main` starts the asynchronous listener before marking Ready, then polls only the signal flags in its normal thread. Startup order is fixed:

```cpp
const Config config = ConfigLoader::load("config/devmanager.json");
const EnvironmentApiKeyProvider provider;
const ApiKeyAuthenticator authenticator(provider.load());
ApplicationBootstrap bootstrap(config);
ReadinessState readiness;
SignalHandler signals;
HttpServer server(bootstrap.service(), bootstrap.logger(), authenticator,
                  readiness, bootstrap.config().server.host,
                  bootstrap.config().server.port);
ServiceLifecycle lifecycle(readiness, signals, server, bootstrap.logger());
server.bind();
server.runAsync();
lifecycle.markReady();
while (!signals.stopRequested()) { /* short normal-thread wait */ }
return lifecycle.stopWhenRequested() == ServiceExit::Stopped ? 0 : 1;
```

Signal callbacks never call `server.stop()`. Normal-thread lifecycle coordination observes signal flags, calls runtime, and maps `Stopped` to exit 0 and timeout/force/failure outcomes to nonzero. Initial exceptions do not mark Ready and use the existing `catch (const std::exception&)` failure path.
