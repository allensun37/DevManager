# DevManager v0.6 API Key Authentication Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 v0.5 HTTP 服务上增加单用户 API Key 认证，同时保持 Domain、ProjectService、Repository、SQLite/JSON 和 CLI 行为不变。

**Architecture:** 认证组件位于 `infrastructure/auth`，由 HTTP 启动入口创建并注入 `HttpServer`。`HttpServer` 在 cpp-httplib 的 pre-routing 边界认证受保护路由；认证成功后才进入现有 `ProjectHttpController` 和 `ProjectService`。CLI 使用原有 `ApplicationBootstrap` 路径，不读取 API Key。

**Tech Stack:** C++17、cpp-httplib、nlohmann/json、GoogleTest 1.17.0、CMake、GitHub Actions Ubuntu/Windows、现有 spdlog。

**Files:**

- [ ] **Step 1: 实现明确接口**

```
class ApiKeyProvider {
public:
    virtual ~ApiKeyProvider() = default;
    virtual std::string load() const = 0;
};

class EnvironmentApiKeyProvider final : public ApiKeyProvider {
public:
    std::string load() const override;
};

class ApiKeyAuthenticator final {
public:
    explicit ApiKeyAuthenticator(std::string expectedKey);
    bool authenticate(std::string_view authorization) const noexcept;

private:
    static bool secureEquals(std::string_view left,
                             std::string_view right) noexcept;
    std::string expectedKey_;
};
```

Provider 使用 `std::getenv("DEVMANAGER_API_KEY")` 读取一次，不 trim，不打印值；缺失或空字符串抛出带变量名的通用错误。Authenticator 构造时拒绝空 key。

- [ ] **Step 2: 实现严格 Bearer 解析和比较**

只接受 `Authorization == "Bearer " + non-empty token`。scheme 区分大小写；缺失 Header、`Basic`、`bearer`、空 token、前后额外空格和 token 不匹配均返回 `false`。比较循环不在字符不匹配时提前返回，并单独合并长度差异；不记录 token。

### Task 3: 在 HttpServer pre-routing 边界接入认证

**Files:**

- Modify: `include/http/HttpServer.h`
- Modify: `src/http/HttpServer.cpp`
- Modify: `CMakeLists.txt`
- Test: `tests/http/ProjectHttpControllerTests.cpp`

- [ ] **Step 1: 扩展 HTTP RED 测试**

将测试中的服务器构造改为显式传入：

```
devmanager::ApiKeyAuthenticator authenticator("test-key");
devmanager::HttpServer server(service, authenticator, "127.0.0.1", 0);
```

新增断言：不带 Header 请求 `/api/projects` 得到 `401`、`error.code == "unauthorized"`、`WWW-Authenticate == "Bearer"`；带 `Authorization: Bearer test-key` 仍得到原有业务结果；`/health` 不带认证仍为 `200`。先构建，预期因 HttpServer 尚未接受认证器参数而失败，保存 RED。

- [ ] **Step 2: 修改 HttpServer 构造和成员**

两个构造函数增加不可拥有的认证器引用：

```
HttpServer(ProjectService& service,
           const ApiKeyAuthenticator& authenticator,
           std::string host,
           std::uint16_t port,
           RequestIdGenerator requestIdGenerator = {});

HttpServer(ProjectService& service,
           Logger& logger,
           const ApiKeyAuthenticator& authenticator,
           std::string host,
           std::uint16_t port,
           RequestIdGenerator requestIdGenerator = {});
```

成员为 `const ApiKeyAuthenticator& authenticator_`。不提供无认证构造函数，避免生产代码意外启动匿名 HTTP 服务；调用方保证认证器生命周期覆盖服务器。

- [ ] **Step 3: 注册 pre-routing 认证处理器**

只保护 `/api/info`、`/api/statistics`、`/api/projects` 和 `/api/projects/<id>`；`/health` 和未知路径不认证。失败响应的核心行为为：

```
response.status = 401;
response.set_header("WWW-Authenticate", "Bearer");
response.set_header("X-Request-ID", requestId);
response.set_content(
    HttpError{401, "unauthorized", "authentication required"}.toJson().dump(),
    "application/json");
return httplib::Server::HandlerResponse::Handled;
```

成功返回 `Unhandled` 进入现有 Controller。失败日志只记录 method、path、status 和 request ID，不记录 Authorization。

在 `CMakeLists.txt` 中把 `DevManagerAuth` 加入 `DevManagerHttp` 的 `PUBLIC` 链接，使 `HttpServer.cpp` 和所有 HTTP 测试都使用同一认证实现；不把认证库链接到 Domain 或 Repository。

## 计划自审

- Provider 只由 HTTP 入口使用，因此 CLI 不会因为缺少环境变量失败。
- Authenticator 不依赖 cpp-httplib；HttpServer 只负责取 Header、Request ID、响应和路由边界。
- ProjectHttpController、ProjectService、Repository 和数据库完全不感知 API Key。
- `/health`、未知路径和 v0.5 业务错误保持原有可用性；受保护业务路径在 Controller 前统一认证。
- 认证失败固定为 401，不区分缺失、格式错误和不匹配，且统一返回 challenge。
- 测试先 RED 后 GREEN，文档/CI 在功能稳定后更新，最后执行完整回归。
