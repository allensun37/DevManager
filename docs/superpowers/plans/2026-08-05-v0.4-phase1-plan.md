# DevManager v0.4 Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Each task follows test-first development and is reviewed for specification compliance and code quality.

**Goal:** Add the v0.4 configuration model/loader, CMake-generated version source, and a small application bootstrap while preserving all v0.3 behavior.

**Architecture:** Configuration is a pure application/infrastructure boundary that reads one local JSON file and returns validated value objects. Bootstrap owns configuration, repository, and manager lifetimes and exposes references for future entrypoint wiring; it does not contain business rules. The CLI and HTTP behavior remain unchanged in this phase except that entrypoints may consume the bootstrap configuration instead of hard-coded defaults.

**Tech Stack:** C++17, CMake 3.20+, nlohmann/json 3.12.0, GoogleTest 1.17.0, existing ProjectManager and JsonProjectRepository layers.

- [ ] **Step 2: Run the focused test and verify RED**

Configure the worktree build and run `ctest --test-dir build -C Debug -R DevManagerConfigTests --output-on-failure`. It must fail because the Config headers/target do not yet exist.

- [ ] **Step 3: Implement the minimal loader**

Define `ServerConfig`, `StorageConfig`, `LoggingConfig`, `Config`, and `ConfigLoader::load(const std::filesystem::path&)`. Defaults are host `127.0.0.1`, port `8080`, storage `data/projects.json`, logging level `info`, logging path `logs/devmanager.log`. Missing files return defaults. Existing files must be an object; known nested fields must have the expected types, non-empty host/level/paths, and a port in `1..65535`; malformed or invalid values throw `std::runtime_error` with a useful field name. Paths remain relative values and are not resolved or created by the loader.
